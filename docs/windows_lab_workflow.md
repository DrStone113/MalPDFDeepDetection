# Windows DEV to REMnux LAB operations

Windows is the source of truth. REMnux receives a reviewed committed source
release and exports only bounded, schema-validated observations. Existing
datasets, checkpoints, source evidence, releases and Python environments are
preserved. No bidirectional synchronization, LAB Internet access or automatic
sample processing is involved.

## Local development and Level 1

Use the new, ignored `.venv-windows-dev` environment for the full declared stack;
the existing `.venv` is retained. To reproduce its creation on a new Windows
host, first verify Python, NVIDIA hardware and driver compatibility, then use:

```powershell
py -3.11 -m venv .venv-windows-dev
.venv-windows-dev/Scripts/python.exe -m pip install --upgrade pip
.venv-windows-dev/Scripts/python.exe -m pip install torch==2.11.0 torchvision==0.26.0 --index-url https://download.pytorch.org/whl/cu128
.venv-windows-dev/Scripts/python.exe -m pip install -e '.[dev]'
.venv-windows-dev/Scripts/python.exe scripts/lab/check_local.py --save
```

The CUDA 12.8 wheel pairing follows the
[official PyTorch version instructions](https://pytorch.org/get-started/previous-versions/#v2110).
Environment installation and a synthetic CUDA operation do not train a model or
establish accuracy. Record actual driver/runtime versions rather than assuming
that a successful import establishes CUDA operation.

`check_local.py` runs the repository guard for the index and worktree, checks
Git whitespace, parses approved Python source without executing it, reads
`pyproject.toml`, runs the reviewed standard-library security suite, checks pip
consistency and imports selected declared modules without opening sample files.
Its timestamped JSON evidence stays under ignored
`artifacts/tmp/maintenance/lab_workflow/`. Failed attempts remain available.

`--stdlib-only` performs the same source checks without importing or claiming
the ML dependency stack. The hook runs the indexed guard and security suite;
GitHub Actions checks the trusted baseline and runs source checks on Windows
and Ubuntu. Configure required checks and PR review separately in GitHub;
workflow files and hooks are writable and do not enforce remote permissions.

The self-tests use generated byte buffers, temporary source trees and disposable
local Git repositories without remotes or inherited hooks. Their synthetic
commits do not alter project history. They exercise header-only Python security
literals, actual-shaped private-key blocks, renamed binary/PDF inputs, late
control bytes, checksums, TAR metadata/padding/traversal/links, schema rejection,
forced-command refusal, response bounds and release/report preservation.

## Content contracts and package identity

`scripts/lab/lab_contract.py` is the shared policy for Windows packaging, LAB
installation, repository content checks and both report readers. All its LAB
copies must be upgraded together with the helpers. No file is exempted by its
security-related filename.

A private-key header is permitted only as an entire, single-line Python string
or bytes literal in syntactically valid Python source, without any matching end
marker. Raw headers, non-Python copies, multiline/escaped key blocks and paired
armor markers are rejected. This distinguishes a detector's inert needle from
credential content; it is not semantic analysis of arbitrary Python programs.

The deployment allowlist includes regular source files under `src/`, `scripts/`,
`tests/`, `configs/`, plus the named overview/build roots in `lab_contract.py`.
Data, reports, figures, weights, archives, hidden files and arbitrary root files
are excluded. The repository guard additionally checks all indexed content,
including preserved research artifacts, against the trusted baseline.

```powershell
python scripts/lab/labctl.py prepare
python scripts/lab/labctl.py prepare --commit FULL_40_HEX_SHA
```

The first command requires a clean checkout. The second deliberately reads only
an explicit existing commit, even when local edits exist. Its output states
`working_changes_included: false`; it cannot release those edits. Review the
actual commit, diff and manifest before approving any deployment. Each TAR
member uses deterministic USTAR metadata, bounded UTF-8 text, SHA-256 and a
canonical path. The receiver rejects extra members, noncanonical headers,
nonzero padding/trailers, links, special files, duplicate paths, forged source
extensions and hash/size disagreement. A valid checksum is integrity evidence,
not approval or trust in a compromised LAB.

## Audit SSH inspection

The client uses Windows OpenSSH, the fixed `192.168.217.10:22` endpoint and
`malpdf-audit`, with the existing `id_ed25519_malpdf_audit` identity only. It
ignores general SSH configuration with `-F none`, disables agent/X11/port
forwarding and multiplexing, requires strict host-key checking, and disables
password/keyboard-interactive authentication. It does not copy private keys.
The pre-existing `remnux-lab-audit` alias can remain for operator convenience;
the helper supplies its own connection restrictions. Unknown or changed host
keys stop the operation and require independent console verification.

```powershell
python scripts/lab/labctl.py status
python scripts/lab/labctl.py audit-check
```

Both stdout and stderr are bounded to 16 KiB, with a 20-second request limit.
Only validated status/report objects are displayed. SSH errors are reported as
exit codes without printing untrusted remote diagnostic text. `audit-check`
tests `id` and an empty shell request; it does not try a write, sudo, a TTY or a
forwarding channel. Those require separately approved server-side/operator
verification. Never infer a complete isolation or privilege audit from these
three probes.

## Bootstrap update: operator approval required

The reviewed bootstrap contains exactly these source files and the canonical
public audit key; it must not contain a private key or corpus data:

| File | Destination |
| --- | --- |
| `scripts/lab/lab_contract.py` | `/usr/local/libexec/malpdf/lab_contract.py` |
| `scripts/lab/lab_side.py` | `/usr/local/libexec/malpdf/lab_side.py` |
| `scripts/lab/lab_readonly.py` | `/usr/local/libexec/malpdf/lab_readonly.py` |
| `scripts/lab/setup_readonly.sh` | Versioned operator bootstrap directory; invoked from the console |
| `id_ed25519_malpdf_audit.pub` | Versioned operator bootstrap directory; only its validated public value is installed |

After the source commit is approved, identify its full SHA and a fresh
`/home/remnux/malpdf-bootstrap/<SHA>` directory. Review per-file SHA-256 values on
Windows and verify them on LAB after the separately approved one-way transfer.
Create the local enumerated bootstrap using
`python scripts/lab/labctl.py bootstrap --commit FULL_40_HEX_SHA`. It contains
only the four listed helper files, the validated public key and `manifest.json`,
under `%TEMP%/malpdf-lab-packages/bootstrap/<SHA>`. It refuses a partial old
commit without the shared contract, unexpected existing files and differing
replacements. It performs no transfer or remote operation.
Do not run a script from arbitrary LAB output. The operator then executes this
exact command from the VMware console, substituting the reviewed SHA:

```sh
sudo sh /home/remnux/malpdf-bootstrap/SHA/setup_readonly.sh /home/remnux/malpdf-bootstrap/SHA/id_ed25519_malpdf_audit.pub /home/remnux/malpdf-bootstrap/SHA
```

This updates root-owned helpers and the single root-owned authorized key,
creates or validates the dedicated account/group, locks password authentication,
and installs `/etc/ssh/sshd_config.d/00-malpdf-audit.conf`. It refuses an existing
audit account with unexpected groups/home/UID or any listed sudo grants. It
backs up previous helpers, key and drop-in under a root-only
`/var/tmp/malpdf-audit-setup.*` directory. It verifies `sshd -t` and effective
settings for the actual Host-only addresses before reloading `ssh`.

The `Match User` block forces the root-owned report endpoint, public-key-only
authentication, the exact authorized-key file, no forwarding, no TTY and no
user RC. `PermitUserEnvironment` is checked in the effective global config; it
is not legal inside this Match block. The installer refuses an effective value
other than `no` instead of changing global SSH policy. These directives follow
the [Ubuntu 24.04 SSHD reference](https://manpages.ubuntu.com/manpages/noble/man5/sshd_config.5.html).
The account still requires a normal login shell for SSH's forced command; the
key and SSHD policy deny arbitrary shell requests. This is not a filesystem
sandbox against local code execution or a compromised SSH/Python runtime.

Verify sudo grants, root ownership and read/write permissions at the console;
verify no sample-path endpoint is exposed. For a forwarding rejection test,
approve a bounded loopback-only request separately after inspecting `sshd -T`;
the helper never enables forwarding to test it. Keep the administrative
credential and session outside Codex's control as required by `AGENTS.md`.

## Source deployment and Level 2

Only the operator may invoke this command from a separately supervised Windows
terminal after approving the exact commit and package manifest:

```powershell
python scripts/lab/labctl.py deploy
```

It requires a clean checkout, an interactive terminal, full-SHA confirmation and
password-authenticated `remnux` access. It uploads only the manifest and TAR to
`/home/remnux/malpdf-inbox`, installs into a new
`/home/remnux/malpdf-releases/<SHA>` directory, and requests AST parsing with the
root-installed helper. It never overwrites an existing release, edits the old
workspace, installs LAB dependencies or selects an active runtime automatically.
Do not supply an administrator password to Codex or script this operation.

The two non-root LAB commands requested by default are:

```sh
/usr/bin/python3 -Es /usr/local/libexec/malpdf/lab_side.py install FULL_40_HEX_SHA
/usr/bin/python3 -Es /usr/local/libexec/malpdf/lab_side.py syntax FULL_40_HEX_SHA
```

The separately approved synthetic command is:

```sh
/usr/bin/python3 -Es /usr/local/libexec/malpdf/lab_side.py synthetic FULL_40_HEX_SHA
```

It runs only the reviewed `scripts/lab/selftest.py --json` from that release as
a non-root Linux user with an isolated temporary HOME, a minimal environment,
no inherited Git credentials/hooks, a 90-second wall limit, 60-second CPU limit,
256 MiB address-space limit, 2 MiB per-file output limit, 64 file descriptors
and 64 per-user processes. A timeout kills the child process group. Process
limits are shared with other processes of the same UID; prefer a dedicated
approved test account for sustained automation. Raw stdout/stderr never enters
the exported report. Linux execution and these resource limits need actual LAB
validation; Windows self-test success is not that evidence.

This tests Python/Git compatibility and the workflow's standard-library security
contract. AST results do not import code; synthetic results do not validate the
ML/PDF parser dependency stack. Report `environment.dependencies` remains
`not_checked`. Any project pytest, LAB dependency audit or import probe requires
separately reviewed commands, environment and output schema. Do not run broad
pytest or install dependencies on LAB by default.

## Sanitized reports

After explicit approval to return the allowlisted JSON, use:

```powershell
python scripts/lab/labctl.py report FULL_40_HEX_SHA --save
```

The forced command interface still permits only `status` and `report <SHA>`.
Schema 2 includes commit, unique run ID, UTC timestamp, `ast_syntax` or
`synthetic_security`, passed/failed/skipped counts, bounded issue descriptors,
and environment system/Python values with isolation/dependencies explicitly
unverified. `file_count` is the total source count for AST or total test cases
for synthetic checks. Unknown keys, malformed counts/status/time, unsafe source
paths, duplicate JSON keys and nonfinite numbers are rejected on both sides.
Runs with skipped tests report `partial`, even if no executed test failed.
Schema 1 remains readable for older AST reports; it lacks the new evidence and
must be identified as legacy. Parser reports are not accepted by this endpoint;
an eventual parser schema must preserve `complete`, `partial`, `failed` and
missing-evidence semantics through a separate approval.

LAB retains unique `<SHA>_<run_id>.json` observations and atomically updates
`<SHA>.json` for the current report. Thus a synthetic run changes which kind is
returned; retrieve and save the AST report before requesting the synthetic run.
Windows saves validated observations under
`%LOCALAPPDATA%/MalPDFDeepDetection/lab_reports/<SHA>_<run_id>.json` and refuses
to replace differing existing evidence. No PDF bytes, recovered strings, raw
tracebacks, private paths or arbitrary serialized objects are returned. LAB can
forge a valid schema; this is containment, not remote attestation.

## Rollback and failure handling

A failed source install deletes only its own temporary staging directory and
leaves older releases alone. Successful installs do not change a current
symlink or running service. Select the previously approved release explicitly
in the operator's launch command to roll back; retain both releases and their
reports. A failed AST/synthetic check returns a nonzero exit code and retains
its sanitized failure report.

The bootstrap restores its prior SSHD drop-in if validation/reload fails;
account/helper/key changes can remain and require console review. It does not
claim transactional account rollback. To revert a successful bootstrap, use the
console to restore the three backed-up helper files and previous authorized key
with root ownership, restore the previous drop-in (or remove the newly created
one if none existed), run `sudo /usr/sbin/sshd -t`, and only then reload `ssh`.
Do not remove the audit user/group or report directories automatically.

If SSH, host keys or isolation checks fail, stop that LAB operation and continue
Windows work. Do not add NAT/bridging/proxies, relax firewall rules, disconnect
an active SSH NIC remotely, or broaden the audit command allowlist.

## Approval batch and Level 3 boundary

Review the Windows diff and verification evidence first. One approval batch
can cover committing only these workflow changes, preparing that resulting
commit, the listed bootstrap/public-key upload and console installation, the
new source release/AST check, a separately identified synthetic run, and the
schema-1/2 report returns after each check. Bind execution to the resulting
full commit SHA, manifest checksums, exact paths and stated limits. Push and
GitHub settings changes remain separate unless explicitly included.

Codex can perform approved read-only audit/report operations and local analysis.
Under the current operator-only rule, it cannot run bootstrap sudo or
`labctl deploy`, or provide their administrative input, even after ordinary
workflow approval. The operator performs that segment in the separate session.

Level 3 remains NOT VERIFIED and is not triggered by either Level 2 command.
Before a real-PDF run, separately approve the actual VM/adapter/route/shared
folder/clipboard controls, sample manifest, non-root command, output schema,
byte/nesting/CPU/RAM/file/process/time limits and snapshot/recovery plan.
`MALPDF_LAB_ISOLATED=1`, Host-only networking or an AST pass alone is insufficient.
